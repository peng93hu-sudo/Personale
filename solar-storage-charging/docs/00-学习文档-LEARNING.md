> 主题：**光储充（光伏 PV + 储能 Storage + 电动汽车充电 Charging）一体化场景** 的市场调研与商业落地
> 区域：**中国（国内）／意大利（Italy）**
> 文档定位：**方法论沉淀** —— 把"如何用多智能体把一件事做到可查、可验证、可追溯"讲清楚。
> 维护：调研 PM + 业务 PM 共同维护；每次大版本由**红军（Red Team）反查**后归档。

## 0. 一句话说清楚这套系统在干什么

> 你（用户）是**项目总 PM / 最终决策人**。
> 你下面有两条独立但咬合的产线，各由一个 PM 负责：
> - **调研线（PM-R）**：把"光储充在中国/意大利到底什么情况"研究清楚，产出**可被审计的研究结论**。

## 1. 为什么要做成"多智能体"，而不是一个 Agent 一把梭

单 Agent 的三个致命问题，正好对应你提的"可查、可验证、可追溯"：

| 单 Agent 的病 | 多 Agent 的解法 |
|---|---|
| **自说自话**：自己查、自己写、自己背书，错了没人拦 | **角色分离**：写结论的人 ≠ 核查结论的人（红军），利益不绑定 |
| **黑箱**：你只看到结论，看不到它怎么来的、信了哪个来源 | **流程显性化**：每条结论=`要点→来源→参数→分析流程→红军判定`，全程留痕 |
| **一锅粥**：研究和业务混在一起，节奏冲突、互相污染 | **产线分离**：调研线按周刷、业务线按天刷，各有 PM、各有成果物 |

**核心设计原则（贯穿全系统）：**
1. **写者与查者分离** —— 任何结论必须由独立的红军反查，红军默认"怀疑"，证据不足即降级。
2. **结论即证据链** —— 没有来源 URL + 时间 + 置信度的"结论"，一律不准进报告。
3. **决策权永远在你手上** —— Agent 只产出"带证据的候选结论 + 参数"，**拍板、调参、改方向是你的**。
4. **成果物驱动** —— 每条产线每个周期必须落一个**看得见的文件**（报告/HTML/方案），不是"我研究了一下"。

## 2. 三层身份模型：决策层 / 管理层 / 执行层

你问到的 **1.PM 2.角色 3.身份 4.工作范畴**，本质是问"每个智能体到底是谁、管什么"。我们用统一的四要素卡片来定义每一个智能体（详见 `01-智能体架构-AGENTS.md`）：

> **【角色 Role】** 它在系统里扮演什么职能（如"政策分析师"）。
> **【身份 Identity】** 它的"人设/专业视角"，决定它用什么标准说话（如"持牌能源政策研究员，只认官方文号"）。
> **【工作范畴 Scope】** 它**能做什么、不能做什么、交付什么**（边界 + 输入 + 输出）。
> **【PM 归属】** 它向哪个 PM 汇报，谁验收它的成果物。

三层：

- **决策层（你）**：定目标、调参数、拍板、验收。系统所有"分叉/取舍"最终汇到你这里。
- **管理层（A0 + 两个 PM）**：把你的目标拆成任务、派工、控节奏、管上下文、管文档版本、对成果物质量负责。
- **执行层（R/B/RT/AR/PUB）**：干具体的活——查、算、写、核、存、出。

## 3. 两条产线的"核心逻辑"（这是你点名要看的）

你明确要求，作为决策人你要能看到每条产线的：
**核心逻辑 → 要点 → 分析结果 → 分析流程 → 每个流程 Agent 的核心要点与考虑的参数**。
下面是两条线的"核心逻辑骨架"，详细 SOP 在 02/03 号文档。

### 3.1 调研线（PM-R）核心逻辑

```
核心逻辑：用"多源交叉 + 红军反查"把不确定的市场信息压成可信结论
要点：政策（能不能做）· 经济性（划不划算）· 格局（谁在做、怎么做）
分析流程：
  ① 拆维度（中×3 + 意×3 = 6维度）
  ② 每维度并行调研（R1/R2/R3 各自 WebSearch+WebFetch，强制带来源）
  ③ 每维度结论 → 红军逐条反查（找独立第二来源，判 confirmed/部分/证伪/无法核实）
  ④ 汇总 + 缺口清单（open questions）→ 你审阅调参
  ⑤ 出 PDF 深度报告 + HTML 看板
每个 Agent 的核心要点与参数：见下表
```

| 流程 Agent | 核心要点 | 关键参数（你可调） |
|---|---|---|
| R1 政策分析师 | 强制配储/独立储能政策、136号文电价市场化、充电基建、容量电价、光储充检试点 | 时间窗（2024-2026）、国家 vs 地方、已落地 vs 征求意见 |
| R2 经济性分析师 | 装机规模、峰谷价差、单站投资与 IRR、电芯/系统成本曲线 | 省份、储能时长（2h/4h）、电价情景、成本年份 |
| R3 格局分析师 | 商业模式（EMC/共享储能/容量租赁/光储充检/V2G）、玩家定位、单站收益结构、痛点 | 玩家清单、模式优先级、案例颗粒度 |
| RT 红军 | 对每条 finding 找独立第二来源、查数字真伪、查来源可达性 | 怀疑强度阈值、必须几个独立源才算 confirmed |

### 3.2 业务线（PM-B）核心逻辑

```
核心逻辑：把调研结论变成"找到货 → 找到客户 → 设计中间流程 → 算得过账"的成交闭环
要点：源头结果（有什么货/服务）· 成交方（谁买谁卖）· 商业模式（中间怎么赚）
分析流程：
  ① 读调研结论 → PM-B 选定 1-2 个"最优商业模式假设"
  ② B1 在源端找产品/货物/服务（设备、EPC、储能系统、CER 运营权…）
  ③ B2 在需求端找客户/成交方（工商业业主、充电运营商、CER 社区、车队…）
  ④ B3 设计中间流程/交易结构（谁出钱、谁运营、怎么分成、合同形态）
  ⑤ B4 财务测算（单站/单项目 IRR、回收期、敏感性）
  ⑥ 红军反查（数字、可行性、合规）→ 你审阅调参 → 出业务 HTML
每个 Agent 的核心要点与参数：见下表
```

| 流程 Agent | 核心要点 | 关键参数（你可调） |
|---|---|---|
| B1 货源 Sourcing | 在源端定位可获取的产品/货物/服务及价格、账期、资质 | 品类、地域、单价区间、MOQ、交期 |
| B2 客户 Demand | 定位真实买方/成交方画像、需求规模、付费意愿 | 客户类型、规模门槛、决策链 |
| B3 成交结构 Deal-Design | 设计交易/分成/合同结构，识别中间利润点 | 模式（自投/EMC/租赁/平台撮合）、分成比例、风险分配 |
| B4 财务测算 | 单项目经济模型、IRR/回收期/敏感性 | 投资额、电价、利用率、补贴、折现率 |
| RT 红军 | 反查数字、可行性、合规与渠道真实性 | 怀疑强度、合规红线清单 |

> **闭环关系**：业务线发现的"缺口/新机会"会反向喂给调研线（例如"意大利 CER 分成机制需要更细数据"），由 PM-R 决定是否纳入下周研究。这就是你说的"PM 判断是否要添加新内容"。

## 4. "可查、可验证、可追溯" 到底怎么落地（机制，不是口号）

这是整套系统的信用基础。三个词分别对应三个机制：

### 4.1 可查（Auditable）—— 每条结论都能点开看见来源
- 每条 finding 的最小数据结构（强制字段）：
  ```json
  {
    "claim": "结论一句话",
    "detail": "支撑说明（含机制/数字）",
    "key_value": "关键量化值，如 峰谷价差0.7-1.2元/kWh",
    "source_name": "来源机构",
    "source_url": "可访问URL",
    "source_date": "发布时间",
    "confidence": "high|medium|low"
  }
  ```
- 所有来源沉淀进 `research/sources.md` **来源登记册**，每个来源给稳定编号 `[S-001]`，正文引用编号。

### 4.2 可验证（Verifiable）—— 红军独立反查，留判定
- 每条 finding 经红军后挂一个 verdict：
  ```json
  {
    "claim": "被核查结论",
    "verdict": "confirmed | partially_supported | refuted | unverifiable",
    "evidence_note": "核查理由",
    "evidence_url": "红军独立找到的佐证/反证",
    "corrected_value": "若原值有误的修正"
  }
  ```
- 报告里**用颜色/标签**区分：✅已证实 / 🟡部分支持 / ❌已证伪 / ⚪无法核实。被证伪的不删除，**降级留痕**（让你看到"我们曾经信过什么、为什么改了"）。

### 4.3 可追溯（Traceable）—— 版本、变更、谁改的都留底
- 每份成果物头部有 **版本块**：版本号、日期、变更摘要、红军批次号。
- 变更日志 `CHANGELOG`：每周/每天的更新逐条记，附"本次因何而改、依据哪条新来源"。
- Git 提交即天然审计线：一次更新 = 一次 commit，commit message 写清"调研周刷/业务日更 + 红军批次"。

> 详见 `05-可追溯与运维-TRACEABILITY-OPS.md`。

## 6. 你（决策人）如何介入与调参

系统给你三个"方向盘"：

1. **改参数**：上文每个 Agent 表里的"关键参数"都是你的旋钮（如把储能时长从 2h 调到 4h、把目标客户从工商业改成充电运营商）。改完重跑对应 Agent。
2. **改方向**：在 PM 层下达"这周重点研究意大利 MACSE 容量拍卖" / "业务线主攻光储充检一体化站"，PM 重新派工。
3. **拍板取舍**：红军给出"A 来源说 X、B 来源说 Y"的分歧时，由你裁决采信哪个，裁决记入 CHANGELOG。

> **重要边界**：Agent **不替你做商业决策**，只把"带证据的选项 + 风险 + 参数"摆到你面前。最终采信、对外动作（找客户、报价、签约）由你确认。

## 9. 我在这次执行里学到/沉淀的要点（给未来复用）

1. **先建机器，再灌数据**：架构文档与研究数据解耦，研究在后台多智能体跑时，前台把系统骨架写完，零等待。
2. **结构化输出是可追溯的前提**：让每个调研 Agent 按固定 JSON schema 交付，红军才有"逐条反查"的抓手，报告才能自动着色。
3. **红军要"利益无关 + 默认怀疑"**：把核查写成独立 Agent、独立找源、证据不足即降级，才挡得住"看起来对其实错"的结论。
4. **节奏分离**：研究（慢、周）和业务（快、日）强行分两条线、两个 PM，避免快线逼着慢线出未经核查的结论。
5. **决策人留旋钮**：每个 Agent 暴露"可调参数"，让你能引导而不是被动接受结果——这是"人在环上(human-in-the-loop)"的落点。

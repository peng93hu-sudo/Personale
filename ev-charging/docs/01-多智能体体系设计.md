# 充电桩调研 × 业务 多智能体体系设计(学习文档)

> 版本:v1.0 · 生成日期:2026-06-28 · 项目PM:Claude Code(主循环编排者)
> 适用范围:充电桩(EV Charging)行业,**国内为主、意大利(及欧盟)为参照**
> 本文是"学习文档",讲清楚:**有多少 Agent、每个 Agent 的身份/角色/工作范畴、它们怎么协作、信息怎么做到可查可验证可追溯、节奏怎么跑、最终决策人怎么介入调试。**

## 0. 一页读懂(TL;DR)

- **谁在干活**:1 个总PM(编排) + 2 条业务线(调研PM线 / 业务PM线) + 1 支贯穿的红军 + 1 条文档可追溯线。
- **角色总数**:**19 个 Agent 角色**;一次"完整跑批"的**实际 Agent 调用约 27~30 次**(因为红军和部分 Agent 按维度并行多实例)。
- **核心铁律**:**每一次更新都必须经过红军反查**;**任何数字/结论都必须挂一个可点击、可核对的来源(URL+出版方+日期)**。无来源 = 不进报告。
- **节奏**:**调研每周刷一次**(PM 判断是否纳入新行业动态/新商业模式);**业务每天产出一个成果物**(成果物=产品本身)。
- **决策人(你)的位置**:站在所有 Agent 之上。你能看到每个流程的"核心逻辑→要点→分析结果→分析流程→每个 Agent 的核心要点与参数",并可**改参数、改维度、改权重来引导结果**,最后拿到 **PDF/HTML/Markdown** 成果。

```
                         ┌─────────────────────────────┐
                         │   最终决策人(你 / 老板)     │  ← 看板 + 可调参数,拥有否决权
                         └──────────────┬──────────────┘
                                        │ 指令 / 调参 / 否决
                         ┌──────────────▼──────────────┐
                         │   总PM(项目经理 · 编排者)   │  ← 排期、拆任务、做最终综合
                         └───────┬───────────────┬──────┘
                                 │               │
                ┌────────────────▼───┐     ┌─────▼─────────────────┐
                │  调研PM线(每周)   │     │  业务PM线(每天)      │
                │  R1..R7 + 综合     │     │  B1..B6               │
                └────────┬───────────┘     └──────────┬───────────┘
                         │  调研结果(JSON+报告)        │  调研结论驱动业务
                         └───────────┬─────────────────┘
                              ┌──────▼──────┐
                              │  红军 Red Team │  ← 贯穿两线,每次更新都反查
                              └──────┬──────┘
                              ┌──────▼──────────────────┐
                              │ 文档与可追溯线           │
                              │ 来源登记 / 报告 / HTML   │
                              └─────────────────────────┘
```

## 1. PM(项目经理)——总指挥的身份与职责

| 维度 | 说明 |
|---|---|
| **身份(Identity)** | 项目总 PM = Claude Code 主循环(编排者)。对**最终决策人**负责,对所有子 Agent 拥有调度与裁决权。 |
| **角色(Role)** | 拆解目标 → 定义 Agent 与工作流 → 排期(调研周更/业务日更)→ 汇总各 Agent 产物 → 把"可决策的结论"交给你 → 接收你的调参并回灌到下一轮。 |
| **工作范畴(Scope)** | ① 维护 Agent 花名册与职责边界;② 定义并维护工作流(本仓库 `workflows/*.workflow.js`);③ 把控质量门(红军未过不发布);④ 维护节奏与触发器(每周/每天);⑤ 维护"可查可验证可追溯"标准;⑥ 把每个流程的核心逻辑/参数透明化给决策人。 |
| **不做什么** | 不替决策人拍板商业方向(只给建议+证据);不绕过红军直接发布;不引入无来源结论。 |
| **关键产物** | 工作流脚本、体系文档(本文件)、排期与触发器、每轮"决策简报"。 |

> **PM 与决策人的分工**:PM 负责"把事情做对、做到可追溯";决策人负责"做对的事"(选方向、定取舍)。PM 给的是**带证据的选项**,不是替你决定。

## 2. 三条线 + 红军:Agent 花名册

### 2.1 调研PM线(Research Line)— 每周刷新

> 任务:把"充电桩行业现状(国内为主、意大利参照)"做成**可决策、可追溯**的调研结论。
> 对应工作流:`workflows/research.workflow.js`

| 编号 | Agent | 身份 | 角色 | 工作范畴 | 关注参数(示例) |
|---|---|---|---|---|---|
| **R-PM** | 调研PM | 调研线负责人 | 定义7个维度、分派、收口、对接红军 | 维度划分、覆盖完整性、来源质量门 | 维度权重、时间窗(近24个月)、地域权重(国内0.7/意大利0.3) |
| **R1** | 政策法规Agent | 政策研究员 | 国内规划/补贴/准入 + 欧盟AFIR/PNRR/GSE | 政策、补贴、桩车比目标、并网准入 | 补贴金额、强制配建比例、合规门槛 |
| **R2** | 市场规模Agent | 市场分析师 | 保有量、车桩比、增长、市场规模、预测 | 数量与金额、增速、2025-2030预测 | 公共/私人/直流占比、CAGR、口径一致性 |
| **R3** | 技术标准Agent | 技术研究员 | 功率/超充/标准(GB/T vs CCS2/ISO15118)/V2G | 标准差异、出海适配 | 功率等级、协议、互认、液冷/SiC |
| **R4** | 竞争格局Agent | 行业分析师 | 国内外 CPO 与设备商、市占、融资 | 玩家排名、集中度、动态 | 桩数/市占率/融资额/扩张计划 |
| **R5** | 商业模式Agent | 商业分析师 | 各类盈利模型、回收期、盈亏平衡 | 单桩经济模型 | 利用率、电价价差、回收期、毛利 |
| **R6** | 供应链成本Agent | 供应链研究员 | 模块/IGBT/SiC/枪线/BOM、出海认证 | 成本拆解、出海壁垒 | BOM占比、认证(CE/CB/RED)、关税 |
| **R7** | 运营用户Agent | 运营研究员 | 利用率、充电行为、痛点、漫游互联 | 真实使用与体验 | 利用率%、充电时长、痛点频次 |
| **R-SYN** | 综合Agent | 首席综合官 | 跨7维度综合为决策结论 + 机会点 | 执行摘要、关键数字、风险、机会 | 置信度、口径冲突调和、机会优先级 |

### 2.2 业务PM线(Business Line)— 每天产出成果物

> 任务:**依据调研结论**,制定机制 → 找货源(源)→ 找客户(成交方)→ 模拟最优商业模式 → 设计中间流程 → **产出成果物(成果物=产品本身)**。
> 对应工作流(下一步建设):`workflows/business.workflow.js`

| 编号 | Agent | 身份 | 角色 | 工作范畴 | 关注参数(示例) |
|---|---|---|---|---|---|
| **B-PM** | 业务PM | 业务线负责人 | 把调研机会变成可成交的业务设计 | 机制、模式选型、流程编排、日更成果物 | 毛利、回收期、可成交性、合规 |
| **B1** | 机制设计Agent | 机制设计师 | 定规则:撮合/分润/定价/风控/履约机制 | 交易机制与激励 | 分润比例、账期、违约、定价锚 |
| **B2** | 源头/货源Agent | 采购/寻源 | 找产品/货物/服务的"源"(厂商/品牌/服务商) | 供给侧画像与触达 | 价格、产能、认证、MOQ、交期 |
| **B3** | 客户/成交方Agent | BD/市场 | 找需求侧(成交方:CPO/车企/地产/经销商) | 需求侧画像与触达 | 采购量、付费意愿、决策链、痛点 |
| **B4** | 商业模式模拟Agent | 商业建模师 | 模拟多套模式打分,选最优 | 候选模式建模+评分 | 单位经济、现金流、壁垒、可复制 |
| **B5** | 流程设计Agent | 流程/交付 | 设计"源→中间环节→客户"的成交流程 | 端到端流程与SOP | 环节数、周期、卡点、转化率 |
| **B6** | 成果物Agent | 产品经理 | 把以上落成"产品本身"(清单/报价/方案/落地页) | 每日成果物产出 | 成果物类型、完成度、可交付性 |

### 2.3 红军(Red Team)— 贯穿两线,质量门

| 维度 | 说明 |
|---|---|
| **身份** | 独立对抗方。**默认"有错直到被证明无误"**,不为任何结论站台。 |
| **角色** | 对每一次更新(调研或业务)做反查:逐条核对来源、识别夸大/过时/幻觉、给 verdict 与置信度、提修正建议。 |
| **工作范畴** | ① 打开每条来源 URL 核对数字与口径;② 交叉验证矛盾数据;③ 标记弱来源/失效链接;④ 对商业模式做"杀死它"式假设压力测试。 |
| **裁决口径** | `verified / partially / unverified / contradicted`;整体 `high/medium/low`。**unverified/contradicted 的论断不得进入对决策人的结论,或必须显式降级标注。** |
| **触发** | **每次更新都触发**(调研每周、业务每天)。红军未过 → PM 不发布。 |

## 3. 工作流(Workflow)— 数据怎么流动

### 3.1 调研线工作流(每周)

```
[决策人设定/沿用参数] 
   → R1..R7 并行调研(各自 WebSearch + WebFetch 原始来源)
   → 每个维度产出 RESEARCH_SCHEMA(含 sources[] 可追溯)
   → 红军逐维度反查(pipeline:某维度调研一完成就立刻反查,不等其他)
   → 产出 REDTEAM_SCHEMA(逐条 verdict)
   → 综合Agent 汇总为 SYNTHESIS_SCHEMA(执行摘要/关键数字/风险/机会)
   → 文档线:写入 data/research.json + docs/02-调研报告.md + web 看板
   → 决策人审阅,可调参数 → 进入下周
```

**为什么用 pipeline 而不是"全部调研完再统一反查"**:pipeline 让每个维度"调研→反查"独立流动,慢的维度不拖累快的,墙钟时间≈最慢的单条链而非各阶段之和。

### 3.2 业务线工作流(每天)

```
[读取最新调研结论 synthesis.businessOpportunities]
   → B1 机制设计 → B2 找源 / B3 找客户(并行)
   → B4 商业模式模拟(多候选打分选最优)
   → B5 流程设计 → B6 产出成果物
   → 红军反查(机制假设、单位经济、可成交性)
   → 文档线:更新当日成果物 + web 看板"业务"页
   → 决策人审阅,可改商业模式/参数 → 次日继续
```

### 3.3 上下文(Context)管理 — "不同 Agent 写作 / 储存 / 跟进"

充电桩这类主题信息量大,**Agent 之间不传原始网页全文,只传结构化 JSON**,避免上下文爆炸:

- **结构化交接**:每个 Agent 输出受 schema 约束的 JSON(数据,不是给人读的话),下游只吃它需要的字段。
- **共享记忆 = 来源登记表**:所有来源沉淀到 `data/research.json` 的 `sources[]`,全局可引用(用 `维度key-Sx` 形式跨维度引用,如 `market-S1`)。
- **储存与跟进**:
  - `data/*.json` —— 机器可读的结构化结果(可追溯的原始证据层)。
  - `docs/*.md` —— 人读的报告(调研报告、业务框架、本学习文档)。
  - `web/index.html` —— 决策人看板(可视化 + 调参入口)。
  - `workflows/*.workflow.js` —— 可重跑、可调参的"活"流程。
- **版本与跟进**:每轮带日期与版本号;周更/日更通过 git 提交留痕,red team 结论一并入库,形成"可追溯审计链"。

## 4. 可查 · 可验证 · 可追溯(三可标准)

这是整个体系的**硬约束**,也是红军存在的理由。

| 标准 | 落地要求 |
|---|---|
| **可查(Findable)** | 每个数字/结论挂 `sourceId`;每个来源有真实 `url`(可点击)、`publisher`、`date`。 |
| **可验证(Verifiable)** | 红军必须**实际打开 URL** 核对来源是否真的支撑该论断、数字是否一致、时点是否最新;给出 `verdict`。 |
| **可追溯(Traceable)** | 从"决策人看到的结论"可一路回溯:结论 → keyNumber → sourceId → 原始来源 URL → 红军 verdict。全链路存于 `data/research.json`。 |
| **置信度分级** | 每维度/每条都有 `selfConfidence` + 红军 `overallConfidence`;低置信度显式标注,不伪装成事实。 |
| **诚实披露** | `openQuestions` / `flaggedClaims` / `confidenceNote` 明确写出"还没证实的"和"数据局限"。**宁可承认不知道,不可编造。** |

## 5. 节奏与触发器(Cadence)

| 线 | 频率 | 触发 | PM 判断点 | 成果物 |
|---|---|---|---|---|
| 调研线 | **每周一次** | 定时 / 决策人手动 | 是否纳入新政策、新玩家、新商业模式 | 更新版调研报告 + 看板 |
| 业务线 | **每天一次** | 定时 / 决策人手动 | 是否切换商业模式、是否换源/换客户 | 当日成果物(清单/报价/方案/落地页) |
| 红军 | **每次更新都跑** | 跟随上面两线 | —— | 反查结论(入库) |

> 落地方式:可用 `/loop` 或定时任务(cron)触发周更/日更;每次触发都重跑对应 workflow,并自动经过红军。

## 6. 决策人介入点(你怎么"改参数引导结果")

你在每一层都能干预,PM 把"旋钮"暴露给你:

1. **改维度**:增/删调研维度(编辑 `workflows/research.workflow.js` 的 `DIMENSIONS` 数组)。
2. **改权重/时间窗/地域**:如把意大利权重从 0.3 提到 0.5,或时间窗收紧到近 12 个月。
3. **改红军严格度**:调高 `effort`、要求 100% 来源逐条 WebFetch、设定"低置信度直接丢弃"。
4. **改商业模式约束**:给 B4 设定硬约束(如"只看可在 6 个月内成交、毛利>20% 的模式")。
5. **否决与回灌**:对任一结论说"不",PM 把你的反馈作为下一轮输入。

**你最终拿到**:① 深度研究 **PDF/Markdown** 报告;② **HTML 看板**(调研+业务);③ 每个流程的"核心逻辑→要点→分析结果→分析流程→各 Agent 核心要点与参数"全透明。

## 7. 数量小结(回答"有多少 Agent")

- **Agent 角色数:19**
  - 调研线:R-PM、R1–R7、R-SYN = **9**
  - 业务线:B-PM、B1–B6 = **7**
  - 红军:调研红军 + 业务红军 = **2**(同一支队伍,两个上场场景)
  - 文档可追溯线:来源登记 / 报告写作 / HTML 可视化 = **3**(可由 PM 主循环兼任,故计为"职能角色")
- **一次完整调研跑批的实际 Agent 调用 ≈ 15**:R1–R7(7)+ 红军×7(7)+ 综合(1)。
- **一次完整业务跑批的实际 Agent 调用 ≈ 12+**:B1–B6 + 各自/分组红军反查。
- **完整一轮(调研+业务)≈ 27~30 次 Agent 调用**,全部产物可追溯入库。

> 数量不是越多越好。维度=覆盖完整性,红军=每条都反查,综合=收口。**多 Agent 的价值在于"分而治之 + 独立对抗验证",而不是堆人头。**
